# Runbook: Argo CD App-of-Apps, External Secrets Operator, and Vault Secret Delivery

**Project:** `sre-decision-intelligence-gitops`  
**Environment:** Kubernetes homelab with Argo CD, External Secrets Operator, and external Vault VM  
**Use case:** Deliver secrets from Vault to Kubernetes workloads using GitOps without committing raw secrets to Git.

---

## 1. Purpose

This runbook documents the full implementation and troubleshooting path used to:

- Configure Argo CD App-of-Apps correctly.
- Manage both Argo CD `Application` and `AppProject` resources through the root app.
- Configure External Secrets Operator to read from Vault.
- Sync Vault-backed Kubernetes Secrets into the `sre-decision-intelligence` namespace.
- Fix Argo CD project destination and whitelist issues.
- Remove persistent Argo CD drift caused by unsupported or non-persisted fields.
- Validate that all Argo CD apps are `Synced` and `Healthy`.

## 3. Key Principle

Do **not** commit raw Kubernetes `Secret` objects with real values into Git.

Git should contain:

```text
ExternalSecret manifests
ClusterSecretStore manifests
AppProject manifests
Argo CD Application manifests
```

Vault should contain the actual secret values:

```text
DATABASE_URL
POSTGRES_USER
POSTGRES_PASSWORD
POSTGRES_DB
```

Kubernetes receives runtime `Secret` objects generated by External Secrets Operator.

## 5. Root App Before the Fix

The root app originally pointed only to:

```yaml
path: argocd/applications
```

That meant Argo CD managed child `Application` manifests, but **not** `AppProject` manifests under:

```text
argocd/projects/
```

This caused project updates, such as `platform-security-project.yaml`, not to be applied by the root app.

## 10. Important Kustomize Behavior

Kustomize does **not** automatically include every YAML file in a folder.

This is intentional and prevents accidental deployment of unfinished or test manifests.

This is valid:

```yaml
resources:
  - projects
  - applications
```

because `projects` and `applications` are directories that each contain their own `kustomization.yaml`.

This is also valid:

```yaml
resources:
  - platform-security-project.yaml
```

because this points directly to a file.

## 11. Bootstrap AppProject Problem

After changing the root app path to `argocd`, the root app started managing `AppProject` resources.

But the root app runs under the `bootstrap` AppProject:

```yaml
project: bootstrap
```

The original `bootstrap-project.yaml` allowed only:

```yaml
namespaceResourceWhitelist:
  - group: argoproj.io
    kind: Application
```

That caused this Argo CD error:

```text
resource argoproj.io:AppProject is not permitted in project bootstrap
```

---

## 12. Correct Bootstrap AppProject

File:

```text
argocd/projects/bootstrap-project.yaml
```

Corrected version:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: bootstrap
  namespace: argocd
spec:
  description: Bootstrap project for Argo CD app-of-apps management

  sourceRepos:
    - 'https://github.com/anselem-okeke/sre-decision-intelligence-gitops.git'

  destinations:
    - namespace: argocd
      server: https://kubernetes.default.svc

  clusterResourceWhitelist:
    - group: ""
      kind: Namespace

  namespaceResourceWhitelist:
    - group: argoproj.io
      kind: Application
    - group: argoproj.io
      kind: AppProject
```

Important addition:

```yaml
- group: argoproj.io
  kind: AppProject
```

---

## 13. Why One Manual Apply Was Needed

This was a bootstrap chicken-and-egg issue.

The root app needed permission to manage `AppProject` resources, but that permission itself lived inside the `bootstrap` AppProject.

So this one-time manual apply was required:

```bash
kubectl apply -f argocd/projects/bootstrap-project.yaml
```

After that, the root app could manage AppProjects through GitOps.

```yaml
      kind: Namespace
    - group: apiextensions.k8s.io
      kind: CustomResourceDefinition
    - group: admissionregistration.k8s.io
      kind: ValidatingWebhookConfiguration
    - group: admissionregistration.k8s.io
      kind: MutatingWebhookConfiguration
```

## 17. API ExternalSecret

File:

```text
platform/external-secrets/workloads/sre-decision-intelligence/api-externalsecret.yaml
```

Example:

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: sre-decision-api-secret
  namespace: sre-decision-intelligence
  labels:
    app.kubernetes.io/name: sre-decision-api-secret
    app.kubernetes.io/part-of: sre-decision-intelligence
    app.kubernetes.io/component: api-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: sre-decision-api-secret
    creationPolicy: Owner
  data:
    - secretKey: DATABASE_URL
      remoteRef:
        key: sre-decision-intelligence/api
        property: DATABASE_URL
```

Critical contract:

```text
Vault logical path:
secret/sre-decision-intelligence/api

Vault property:
DATABASE_URL

Kubernetes Secret:
sre-decision-api-secret

Kubernetes Secret key:
DATABASE_URL
```

## 20. Vault KV v2 Path Rule

The `ClusterSecretStore` is configured with:

```yaml
path: secret
version: v2
```

Therefore, in `ExternalSecret.remoteRef.key`, use:

```yaml
key: sre-decision-intelligence/api
```

Do **not** use:

```yaml
key: secret/data/sre-decision-intelligence/api
```

The `secret/data/...` path is the internal Vault KV v2 API path. External Secrets Operator handles that internally when the store is configured with:

```yaml
path: secret
version: v2
```

## 21. Vault Commands Used

### API secret

Use a consistent DB user and URL.

Example if using `sre`:

```bash
vault kv put secret/sre-decision-intelligence/api \
  DATABASE_URL="postgresql+psycopg://sre:sre_password@sre-decision-postgres:5432/sre_decision_intelligence"
```

Example if using `sre_user`:

```bash
vault kv put secret/sre-decision-intelligence/api \
  DATABASE_URL="postgresql+psycopg://sre_user:sre_password@sre-decision-postgres:5432/sre_decision_intelligence"
```

### PostgreSQL secret

Example if using `sre`:

```bash
vault kv put secret/sre-decision-intelligence/postgres \
  POSTGRES_DB="sre_decision_intelligence" \
  POSTGRES_USER="sre" \
  POSTGRES_PASSWORD="sre_password"
```

Example if using `sre_user`:

```bash
vault kv put secret/sre-decision-intelligence/postgres \
  POSTGRES_DB="sre_decision_intelligence" \
  POSTGRES_USER="sre_user" \
  POSTGRES_PASSWORD="sre_password"
```

Important:

```text
POSTGRES_USER and DATABASE_URL must match.
```

## 23. ClusterSecretStore Drift Issue

The app `external-secrets-platform-config` remained `OutOfSync` even after sync.

Diff showed:

```diff
>           audiences:
>           - vault
```

This meant Git declared:

```yaml
audiences:
  - vault
```

but the live `ClusterSecretStore` did not persist that field.

Because the backend was already:

```text
Healthy
Valid
ReadWrite
Ready=True
```

the field was removed from Git.

---

## 24. Why `audiences` Was Removed

The `audiences` field is used in stronger Kubernetes token audience setups, often when Vault roles are configured with a matching audience such as:

```text
bound_audiences = vault
```

But in this implementation:

- Vault auth was already working.
- ESO backend was healthy.
- Kubernetes/ESO was not persisting the field.
- Argo CD stayed permanently `OutOfSync`.

Therefore, this block was removed:

```yaml
audiences:
  - vault
```

This fixed the Argo CD drift.

## 34. Troubleshooting: InvalidSpecError Destination Not Allowed

Error:

```text
application destination server 'https://kubernetes.default.svc'
and namespace '<namespace>'
do not match any of the allowed destinations in project '<project>'
```

Fix:

Update the relevant `AppProject`:

```yaml
destinations:
  - namespace: <namespace>
    server: https://kubernetes.default.svc
```

Then ensure the project file is included in:

```text
argocd/projects/kustomization.yaml
```

Then sync root:

```bash
argocd app sync sre-platform-root
```

## 37. Troubleshooting: Argo CD App Stays OutOfSync After Successful Sync

Run:

```bash
argocd app diff <app-name>
```

If the diff is a field that the Kubernetes API or controller does not persist, either:

1. Remove the unsupported/unneeded field from Git, or
2. Configure Argo CD ignore differences for that field.

In this implementation, `audiences` was removed from `ClusterSecretStore` because Vault auth worked without it and it caused permanent drift.

Check the ExternalSecret:

```bash

```


```text
READY: True

```

Check Vault path:


Common causes:

## 40. Vault Seal Monitoring Script

Optional monitoring script:

```bash
#!/usr/bin/env bash
set -euo pipefail

export VAULT_ADDR="https://vault.platform.local:8200"
export VAULT_CACERT="/home/jumpbox/.vault-tls/vault-ca.crt"

LOG_FILE="/var/log/vault-seal-check.log"

STATUS_JSON="$(vault status -format=json 2>/tmp/vault-status-error.log || true)"

if [ -z "$STATUS_JSON" ]; then
  echo "$(date -Is) ERROR: Unable to contact Vault. $(cat /tmp/vault-status-error.log)" >> "$LOG_FILE"
  exit 1
fi

SEALED="$(echo "$STATUS_JSON" | jq -r '.sealed')"

if [ "$SEALED" = "true" ]; then
  echo "$(date -Is) WARNING: Vault is SEALED. Manual unseal required." >> "$LOG_FILE"
  exit 2
fi

echo "$(date -Is) OK: Vault is unsealed." >> "$LOG_FILE"
exit 0
```

## 45. Important Warnings

- Do not commit raw secret values into Git.
- Do not store Vault unseal keys on the Vault VM.
- Do not use `secret/data/...` inside `ExternalSecret.remoteRef.key` when the store already uses KV v2.
- Do not manually `kubectl apply -k` resources that Argo CD owns unless it is a deliberate bootstrap or emergency recovery.
- Always check `argocd app diff` before guessing why an app is OutOfSync.
- Keep Kubernetes Secret names and keys stable so Deployments do not need unnecessary changes.
